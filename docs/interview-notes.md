# 项目面试口径与追问

## 90 秒项目介绍

“这是一个企业知识库与工单处理 Agent。用户上传企业制度后，系统先做文档解析、
切片和索引；提问时经过业务查询改写、BM25 与向量混合召回、Rerank，再把有限
证据交给模型生成带引用的回答。高风险、低置信或证据不足时，LangGraph 会走
人工交接分支；可自动解决的问题则通过工具创建工单。项目还实现了多轮会话、
SSE Token 流式输出、模型超时重试、Token 统计和 57 条离线评测。”

## 关键取舍

### 为什么用 LangGraph

业务流程有明确状态和条件分支：准备、检索、生成、创建工单或转人工。LangGraph
让节点、状态变化和工具调用可观察，比把所有逻辑塞进一个函数更容易测试和排错。

### 为什么不让模型直接决定风险

资金盗刷、账号安全、监管投诉等风险需要稳定、可解释的服务端规则。模型负责
基于证据组织回答，不能覆盖 `P0/P1` 和工具边界。

### 为什么仍然保留关键词检索

当前离线向量是哈希特征，不是真正的神经语义 Embedding。57 条内部评测中，
纯向量 Hit@1 低于关键词检索，因此使用较低向量权重，并保留 BM25 作为稳定基线。
如果替换为中文 Embedding，需要用独立数据重新评估权重。

### 为什么 Rerank 是启发式

当前没有引入第二个模型调用，Rerank 使用标题覆盖和证据覆盖率做轻量调整。
它的价值是建立可替换接口；真正上线时应比较 Cross-Encoder 的质量、延迟和成本。

### 如何避免模型编造

- 只把通过阈值和重排的证据发送给模型；
- Prompt 明确禁止编造金额、时效和办理结果；
- 返回结果保留 service 端的 citations；
- 证据不足直接回退和转人工；
- 服务端风险策略优先级高于模型文本。

### 如何处理模型故障

- HTTP 超时；
- 有限指数退避重试；
- 429 和 5xx 分类处理；
- 最大并发信号量；
- 流式响应在尚未输出 Token 时可重试；
- 非流式失败回退到本地抽取式答案。

### 如何设计评测

- 分类与优先级使用人工构造的业务问法；
- 检索对比 lexical、vector、hybrid、hybrid_rerank；
- 指标使用 Hit@1、Hit@3、MRR 和平均延迟；
- 高风险降级是单独指标，因为漏判成本高于普通排序错误；
- 承认当前数据与规则来自同一批样本，下一步需要独立盲测。

## 高频追问

### 如果知识库中没有答案

检索相关性低于阈值时不生成事实性回答，创建待人工工单，并明确告知用户。

### 多轮上下文怎么处理

会话消息持久化到 SQLite。只有短问题或包含“那、这个、超过、怎么办”等指代时，
才拼接最近两轮用户问题，减少上下文污染。

### 流式怎么实现

模型侧读取服务商返回的 SSE，逐块提取 `choices[0].delta.content`；应用侧再把
Agent 节点和答案增量转成浏览器可消费的 SSE。

### 如果并发量变大

当前 SQLite 和线程本地服务适合展示。生产需要迁移到 PostgreSQL，引入任务队列、
Redis 限流、集中式向量库、模型调用配额和链路追踪。

### 这个项目最值得改进什么

1. 用真实中文 Embedding 和 Cross-Encoder 替换离线哈希基线；
2. 使用独立盲测集和真实工单评估；
3. 补 PDF/DOCX 解析质量；
4. 加入登录、租户隔离、RBAC 和审计；
5. 做端到端延迟、成本和调用成功率的持续监控。

## 可以写进简历的表述

- 使用 FastAPI、LangGraph 和 SQLite 构建企业知识库与工单 Agent，支持文档上传、
  混合检索、引用溯源、多轮会话和 SSE 流式输出。
- 设计 knowledge_search、create_ticket、handoff_ticket 等可审计工具节点，将
  高风险与低置信问题转入人工流程。
- 构建 57 条离线评测，比较关键词、向量、混合与 Rerank 方案；内部回归 Hit@3
  为 100%，优先级降级漏判为 0。
- 接入 OpenAI 兼容模型，实现超时、重试、并发限制、Token 用量记录和离线回退。

## 面试中的诚实边界

可以说明代码在 AI 编程助手辅助下完成，自己主要负责需求定义、架构选择、业务数据、
验收、评测、问题定位和迭代决策。不要声称独立手写了全部代码，也不要声称当前
离线哈希向量是“语义模型”。能解释关键取舍和已知缺陷，比夸大实现更重要。
